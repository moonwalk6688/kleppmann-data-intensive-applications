## 数据模型是逐层抽象

应用先把现实人、组织、交易建为对象/API，再映射到关系表、文档或图，数据库继续映射为字节和硬件信号。每层模型隐藏下层复杂度，也把某些操作变得容易、另一些变得困难。选模型要从数据结构、关系与查询演化出发，而非只看产品标签。关系模型的长期价值在于将存储访问路径交给数据库优化器；NoSQL 包括多种不同技术，不能作为一个单一模型来比较。

## 文档与关系：关系形状决定取舍

一份履历包含用户基本信息及多份经历、教育和联系方式，构成以用户为根的一对多树。整份资料经常一起读取时，JSON 文档的局部性和应用对象形式很自然；关系设计则可把各段拆表，读时 join 或多次查询。文档不是没有模式，通常只是**读时解释隐式模式**；写时模式在入库时约束结构。异质、外部不可控的数据可能适合读时模式；所有记录应一致时，显式模式有文档化和检查价值。无论哪种模式，旧记录与新字段共存都需迁移/兼容策略。书中对具体数据库 ALTER 行为的描述是 2017 年背景，不能当作今日保证。

当地区、行业、学校、企业和推荐人独立存在并需共享或更新时，数据出现多对一、多对多关系。用稳定 ID 引用可减少人类可读名称的重复与更新不一致，但必须解析引用。关系库擅长 join；文档库若不支持或弱支持 join，工作转到应用，反规范化又需同步副本。文档局部性只在**常一起读取文档大部分**时有利；只读小块或频繁扩展文档可能付出额外 I/O/重写成本。关系库可存 JSON/做局部聚集，文档库也可能加 join；实现能力需按现行版本核验。

历史对照：IMS 层级模型擅长树，CODASYL 网络模型允许多父但要求程序手工导航访问路径，结构改动会牵连应用代码。关系模型用表、键和声明式查询把访问路径交给优化器。现代文档引用并不等同于 CODASYL 指针；图数据库也不等同于旧网络模型，因为图节点可独立索引，边可自由连接且支持声明式查询。

## 声明式查询与 MapReduce

SQL 表达需要什么结果，优化器选择索引、join 顺序与执行方式；命令式代码固定遍历步骤，容易与存储顺序耦合。声明式形式也更方便实现并行和内部优化。作者用 CSS/XPath 对比 DOM 命令式操作说明：规则声明了状态变化后的目标结果，浏览器可重新应用；一次性直接改 DOM 样式会留下状态同步问题。

MapReduce 的 map/reduce 纯函数可被框架并行、重试，但写两个相互配合的函数比简单聚合 SQL 更繁琐。SQL 也能分布式执行，MapReduce 不是分布式查询的唯一方式。MongoDB 聚合流水线说明文档数据库也会加入声明式查询能力。章节中的 MongoDB 版本与 API 只作历史例子。

## 高连接数据与图语言

当“任何实体都可能与别的实体关联”、关系类型多或路径长度不固定时，图模型更自然。属性图的顶点与边各有 ID 和属性，边记录起终点与关系标签，支持双向遍历。可用关系表表示图，但可变长度路径在 SQL 中往往需递归 CTE，书中用“出生在美国、住在欧洲”与多级地理包含关系比较 Cypher 简洁路径匹配和 SQL 递归表达。图的优势不是绝对查询性能，而是这些关系形状的表达与演化。

三元组存储将信息表示为主体—谓词—客体；客体为值时相当于属性，为节点时相当于边。RDF/URI 命名空间旨在跨来源合并时避免同名歧义，不意味着应用必须接受“语义网”愿景。SPARQL 用路径表达图模式；Datalog 用可复用、递归的规则推导新关系，复杂逻辑可逐步组合，但一次性简单查询不一定方便。OCR 中这些语言的示例代码受损，精确语法须查原书清晰版本和当前规范。

## 选型步骤

1. 画实体与关联：记录主要是一对多树、稳定表关系，还是多类型多对多网络。
2. 列最重要的查询与写入：整文档读取、局部更新、跨实体 join、路径遍历、聚合，以及未来新增关联的可能性。
3. 写下结构约束与演化方式：入库检查、读时兼容、迁移窗口和旧客户端。
4. 以真实数据量和查询验证局部性、索引、join、递归及同步成本；把缓存和反规范化维护算进总成本。
5. 复核可移植性与团队熟悉程度。关系、文档和图可以互相模拟，但表达与运行成本不同；一套系统不必解决所有任务。
