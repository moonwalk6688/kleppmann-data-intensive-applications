## 分区解决容量与吞吐，复制解决冗余

分区把每条记录分配给一个逻辑子集，使数据和请求分摊到多个节点；每个分区仍可有多个副本。分区收益取决于负载均匀，偏斜会造成热点：若十个节点中一个承受大多数流量，扩容并不会线性提高吞吐。先分析键分布和访问分布，不只统计数据行数。

## 分区键：范围与哈希

**键范围分区**保留排序，适合按键区间扫描与相邻记录共址；边界应随数据分布调整。若时间戳作首列且写入永远落在最新时间段，会形成当前分区热点。可把传感器 ID 置于时间前，分散写入，但跨传感器查同一时间段需要多个范围查询。

**哈希分区**把键散到哈希空间，通常分布更均匀，但相邻键被打散，主键范围查询往往需要跨分区。复合键可用前缀确定分区、其余字段在分区内排序，例如 user_id 分区、update_timestamp 排序；同一热门 user_id 仍可成为热点。对单个极热键可加随机后缀拆成多个键，写入分散，读取需聚合，且要维护哪些键被拆分。哈希函数应在所有进程中稳定，不能随意使用语言对象哈希。书中“consistent hashing”指一种重平衡方法，不是副本或 ACID 一致性；具体数据库术语可能不精确。

## 二级索引的读写取舍

**本地/文档分区索引**与记录存同一分区，单记录写只改该分区；按次级字段查找时可能向所有分区 scatter/gather，再合并结果，分区越多尾延迟越受慢分区影响。**全局/词项分区索引**按被索引的 term 自行分区，读某个 term 可定向，但一次记录写可能更新多个远端索引分区，写入更慢、协调更复杂；全局索引常异步更新，紧随写入的查询可能找不到记录。选索引时列出高频查询及新鲜度要求，测量 scatter/gather 和索引传播延迟。

## 重平衡与请求路由

扩容、数据增长和节点故障都需要重平衡。验收标准是：负载更均匀、迁移时继续服务、迁移数据尽量少。直接用 hash(key) mod 节点数会在节点数量变化时搬动大量键。更可控的方式包括：固定较多分区并在节点间搬迁；按数据量动态分裂/合并分区；让分区数随节点数变化。固定分区数需预估未来扩展上限与单分区大小；动态范围分区的空库初期可能只有一个分区，需要预分裂；自动重平衡可能与误判故障相互放大而形成级联过载，必要时让运维审核迁移计划。

客户端可以连接任一节点转发、经专门路由层，或自己维护分区映射直连。无论哪种，关键是所有决策者得到同一份“分区→节点”最新映射；可由协调服务维护权威元数据，也可用 gossip 传播，具体方案有不同一致性与运维成本。MPP 分析查询会把 join、过滤、分组、聚合拆成跨节点执行阶段，不能套用单键路由模型。

## 架构评审步骤

1. 列出主要读写模式、分区键候选、时间增长方向与单键热度；估算最热分区而非只看平均值。
2. 比较范围键、哈希键和复合键在点查、范围查询、跨实体查询上的代价。
3. 明确本地或全局二级索引的写入、查询扇出、索引新鲜度及尾延迟。
4. 在扩容和节点故障演练中测迁移数据量、服务中断、路由映射收敛与负载峰值。
5. 对跨分区操作标出部分成功的业务后果，留给事务/协调方案处理，不把“分区独立”误认为操作自动原子。

**自测**：为什么时间戳范围键会造成写热点？复合键如何兼顾分散与分区内范围查询？本地索引与全局索引分别把成本放在读还是写？为什么 hash mod N 不适合扩容？自动重平衡何时可能加剧故障？
