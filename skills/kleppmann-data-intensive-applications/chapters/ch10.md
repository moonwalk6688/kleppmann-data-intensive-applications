## 服务、批处理和流处理

在线服务以请求响应时间和可用性为核心；批处理对固定、有限输入运行作业，主要看吞吐量；流处理对持续到来的无界输入处理，主要看事件到结果的延迟。三者不是同一场景中的互斥产品，而是不同数据流形态。先问输入有无边界、是否有人等待结果、结果多久必须可见。

## Unix 管道到分布式批处理

Unix 工具以字节流/文件描述符作为统一接口。小程序各做一件事、标准输入输出拼接、输入不变且中间结果可观察，使试验、重跑和调试容易。日志计数例子用 awk 提取键、sort 排序、uniq 聚合；内存哈希聚合适合不同键数量可装内存的情况，外排序可处理超内存工作集。纯文本解析会有脆弱字段索引，生产数据应明确 schema 与记录边界。

MapReduce 将类似模式扩展到分布式文件系统：输入按块拆成 map 任务，mapper 对记录发出键值对；框架按键分区、排序、shuffle；reducer 对同键值迭代处理。计算尽量靠近输入副本，输出文件顺序写入且作业完成才发布。HDFS 的 NameNode 维护块位置，块通过复制或纠删码容错。MapReduce 工作流的阶段一般通过目录与调度器连接；每段完成后下一段才启动。

## Join、倾斜与数据布局

Reduce-side sort-merge join 把两侧按同一键映射、分区、排序，让同键记录在一个 reducer 相遇；对输入布局要求低，但 shuffle/排序昂贵。组聚合和会话化也靠同键汇聚。热键会造成慢 reducer，可抽样识别、拆分热键并复制另一侧，或分两级聚合，代价是额外复制与复杂度。

Map-side broadcast hash join 适合一侧能装入每个 worker 的内存/本地索引；大表分区逐一扫描，小表复制到各 worker。Partitioned hash join 要求两侧同键、同哈希、同分区数；map-side merge join 还要求对应分区已按键排序。选择算法之前，记录大小、基数、倾斜、分区/排序元数据和网络成本；不要仅看逻辑表结构。

## 输出语义与容错

批处理常输出搜索索引、推荐表或只读 KV 文件供在线服务使用。避免 mapper/reducer 逐条直写生产库：会受网络往返限制、冲击在线服务，并让失败作业的部分副作用泄露。更稳妥的流程是写不可变新版本，验证后批量加载并原子切换读版本，保留旧版可回滚。框架重试仅在输入不可变、任务确定性足够、失败输出被丢弃且外部副作用受控时才能维持作业结果语义。

MPP 数据库擅长优化分析 SQL；HDFS 与 MapReduce 提供任意文件格式与自定义代码的开放数据处理平台。原始数据先收集再 schema-on-read 有利于不同使用者探索，但会把解释负担转给消费者。MapReduce 频繁落盘和任务粒度重试的取舍，与当年多租户集群高频抢占有关；不能照搬成所有现代作业的最优选择。

## 数据流引擎和图处理

Spark、Tez、Flink 等把多算子作为一个数据流作业，按需分区、排序、广播，减少无谓的中间态完整物化。代价是节点失效后可能从 lineage 或 checkpoint 重算；随机数、时钟、外部数据与无序遍历会破坏确定性，必要时固定种子或物化昂贵中间态。排序必须看完整输入才可产出全序结果，其他算子可流水线化。

图算法的图是**数据自身的边和顶点**，不同于算子组成的 DAG。Pregel/BSP 按超步给顶点发消息并保留顶点状态，迭代到收敛；跨机消息与检查点带来成本。图能放单机内存或磁盘时，先比较单机算法。声明式 join/过滤/聚合可让优化器选择算法、列裁剪和向量化；自定义函数保留灵活性，但会降低优化空间。

## 使用流程

1. 定义有限输入快照、作业完成条件、结果时效与验收指标。
2. 画出数据流 DAG、权威输入、派生输出、每段的分区与排序属性。
3. 对 join 量化大小和倾斜，选择 reduce-side、broadcast、partitioned hash 或 merge。
4. 确认重试确定性、状态检查点、外部副作用、部分失败隔离及版本切换。
5. 先用小数据验证输出，再测峰值内存、shuffle 字节、长尾任务和恢复时间。

**自测**：批处理与流处理的关键边界是什么？为何热键导致长尾？什么条件使 broadcast join 合适？为何直接在 reducer 中写生产库有风险？数据流引擎减少物化后如何恢复故障？
