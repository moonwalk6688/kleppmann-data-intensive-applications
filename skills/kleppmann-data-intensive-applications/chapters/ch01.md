## 数据系统是组件组合后的整体保证

应用常把数据库、缓存、搜索索引、消息队列、批处理器拼成一个服务。工具类别边界并不绝对：有的存储也承担队列用途，有的队列提供持久化。当应用代码负责让主库、缓存和索引同步时，开发者事实上在设计一个新数据系统；外部 API 给出的“写入后看到什么”“数据何时可搜索”等保证来自整条链路，不能仅看单个组件能力。选型还受团队经验、遗留系统、交付期限、风险偏好与法规限制影响。

## 可靠性：区分 fault 与 failure

可靠指系统在硬件故障、软件缺陷和人为错误下继续按要求工作，包括功能、性能和安全。**fault** 是组件偏离预期，**failure** 是整体服务不能满足用户要求；有 fault 不一定导致 failure。容错必须说明针对哪类故障，没有系统能对所有故障容错。故意注入可恢复故障可验证恢复机制，但安全泄露等不可逆事件更重预防。

硬件故障相对随机，可用冗余、备份和跨机器容错缓解。软件错误常因隐藏假设、共同依赖或级联故障而相关，复制同一程序并不消除系统性 bug；需要隔离、测试、监控、自我校验与恢复。人为错误通过清晰界面、低风险沙箱、逐步发布、快速回滚、数据重算、可观测性和培训减轻。书中云实例、磁盘寿命和故障比例是历史案例。即使普通照片或电商应用，数据损失和停机也会影响真实用户；在原型阶段有意降低可靠性标准可以，但必须知道代价。

## 可伸缩性：先描述负载和性能

“能扩展”不是系统的固定标签，必须先定义负载参数与增长方向：请求/秒、读写比、同时在线人数、缓存命中率、对象大小、关注者分布等。Twitter 2012 年时间线案例比较两条路径：读时汇总关注者推文，写便宜而读贵；写时扇出到关注者时间线，读便宜而写负担重。平均粉丝数掩盖巨星账号的极端扇出，于是混合方案让普通用户写时扇出，巨星在读时合并。这里的数值与架构只作为当年案例；关键方法是识别**决定瓶颈的负载分布与极端值**，再选读写工作分配。

性能要回答两个问题：资源固定，负载增加后性能怎样变？要求性能不变，资源需增加多少？批处理通常关心吞吐或总作业时间，在线服务关心端到端响应时间。作者区分服务时间、排队/网络与用户实际响应时间；“latency”在不同社区常混用，测量口径要写清。响应时间是分布，p50 看典型体验，p95/p99/p999 看尾部；并行调用多后端会放大尾部。队头阻塞和排队使客户端实际等待可能远高于服务端处理时间。压测客户端若等上一请求完成才发下一请求，会人为压低真实排队。分位数不能简单取各机器分位数平均，应汇总原始观测或直方图再算。

纵向扩容、横向扩容、弹性伸缩和人工扩容各有操作成本；无状态服务易分布，带状态数据库跨节点更复杂。系统需要的扩展方案随读/写量、数据大小、访问模式和延迟要求变化；初创产品为假设流量预先造复杂架构，可能拖慢验证。作者主张用实际负载和每一级数量级增长重新审视架构。

## 可维护性：三种具体能力

**可操作性**：监控运行、定位故障、打补丁、容量规划、部署配置、迁移、文档和知识传承都易做；默认行为可预测且管理员能在必要时干预。**简洁性**：减少紧耦合、特例和意外复杂性；抽象隐藏实现细节而保留清晰的行为保证，功能多不必然复杂。**可演化性**：团队能随业务和技术变化改动整套数据系统，包括跨服务迁移，而不只是在单文件中重构。好的抽象和运行模型降低变更成本。三者共同决定长期维护费用。

## 诊断练习

给一个真实服务写出：用户可见的正确性与故障边界；前三个负载参数及其分布；客户端 p50/p95/p99 与作业吞吐；负载翻倍时资源与性能的预测；主库/缓存/索引的同步保证；一次节点、依赖或人为错误如何恢复；运维人员是否能观察、回滚并理解系统。明确哪些是已测数据，哪些只是估算。
