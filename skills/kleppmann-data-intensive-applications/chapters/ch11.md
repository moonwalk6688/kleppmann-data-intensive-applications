## 消息系统的首要决策

事件是有时间戳的不可变事实，由生产者写入 topic/stream，由消费者处理。先确定生产快于消费时的策略：丢弃、缓冲还是反压；再确定节点离线时能否丢消息、保留多久、怎样发现积压。传统消息代理以逐消息分配和 ack 为中心，适合任务队列、处理顺序不重要的工作；崩溃后的重投递可能打乱全局顺序。日志型代理按分区追加，分区内 offset 单调递增、顺序可重放，适合高吞吐、多个独立消费者、重建派生视图；跨分区不保证顺序。消费者组内并行度受分区数限制，慢消息可阻塞同分区后续消息。保留期是有界缓冲，监控消费 lag 与最旧 offset，避免超期造成不可恢复缺口。

## 从数据库变更到派生视图

应用双写数据库和索引会遇到并发写顺序相反或部分写入失败，导致永久分歧。CDC 从一个权威库的提交日志提取变更，把搜索索引、缓存、仓库作为异步派生消费者；必须处理 schema 变更、复制延迟、顺序和重放。新消费者需要与日志位点对齐的**一致快照**；按主键保留最近值的日志压缩可供重建当前状态，删除要用 tombstone 处理。

Event Sourcing 与 CDC 不同：应用把语义明确的**事件**作为原始事实写入不可变日志，当前状态从事件重放生成；CDC 则在普通可变数据库之下抽取变更。先验证命令，成功接受后才发布事件；消费者不能事后拒绝已经成为事实的事件。事件通常不能简单按键压缩，因为以前的事件可能影响最终状态；快照可加速恢复，但需保留可重放历史。可从同一日志构建多种读视图（CQRS）。异步视图有“写后立刻读不到”的延迟，需显式实现读己之写、等待位点或同步读路径。无限保留事件有存储和真实删除/隐私难题，设计时明确保留与删除策略。

## 流处理的时间与 Join

CEP 找事件序列模式；流分析做速率、滚动统计与窗口聚合；物化视图维护需要长期状态。**事件时间**描述事情发生时刻，**处理时间**是工作节点见到它的时刻；积压恢复会让处理时间统计出现假峰值。迟到事件策略需定明：丢弃并统计，还是发布更正/撤回；多源输入要处理各源进度。设备时钟不可信时记录发生、发送、服务端接收时刻并估计偏移。常见窗口：滚动（不重叠）、跳跃（重叠固定步长）、滑动（按事件间隔）、会话（以不活跃间隔关闭）。

流流 Join 在限定时间窗内匹配两个事件，状态与过期策略重要；流表 Join 用 CDC 维护本地维表副本以实时丰富事件；表表 Join 维护两个可变表的连接物化视图。跨流到达顺序未定会让历史重放产生不同结果；涉及税率等历史属性时，事件应携带维度版本，按发生时有效版本 Join，而非读取当前值。

## 故障恢复与有效恰好一次

无限流不能等作业结束才发布。微批、checkpoint 和状态快照可在框架内部恢复，但外部数据库写、发邮件等副作用仍可能重复。想达到可见的“恰好一次”，必须把输入 offset、算子状态和输出同一事务提交，或用幂等写入。幂等更新可携带原事件 offset/版本并原子比较；前提是重放顺序与处理确定性，且没有别的节点同时改同一值。故障切换需 fencing 旧节点。状态可以远端保存、周期 checkpoint、紧凑日志恢复或从输入重放，按恢复时间和成本选择。

## 设计检查

1. 对每个 topic 定义事件 schema、键、分区、保留期、最大消费积压与丢失容忍度。
2. 定义权威源与派生视图、快照日志位点、重建流程、延迟上限和一致性校验。
3. 定义时间口径、窗口边界、迟到更正、跨源版本与 Join 状态生命周期。
4. 模拟消费端处理成功但 ack/offset 提交失败，检查重复输出。
5. 演练旧节点恢复、分区再平衡、checkpoint 丢失、重放及外部副作用。
