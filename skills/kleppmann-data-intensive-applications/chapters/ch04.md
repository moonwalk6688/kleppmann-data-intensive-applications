## 兼容性是部署能力

功能变化常伴随数据模式变化，但滚动升级期间新旧服务同时运行，客户端更可能长期停留旧版本。**向后兼容**：新代码读旧数据；**向前兼容**：旧代码读新数据。要为数据、API 请求、响应和消息分别设计兼容性，避免把“所有节点同一瞬间升级”当作前提。编码是内存对象与文件/网络字节之间的转换；本章的 serialization 指编码，不是第 7 章的事务可串行化。

## 格式选择与数据类型

语言自带对象序列化方便，却常绑定单一语言、缺乏版本演化；反序列化不可信字节可能实例化任意类，造成安全风险，跨进程/长期存储应谨慎。JSON、XML、CSV 便于跨组织交换，但数字精度、整数/浮点区别、二进制内容、CSV 转义和可选模式需要明确约定。大于 2^53 的整数若被 JavaScript 以双精度浮点解释可能失真。Base64 可把二进制转文字，却增加约三分之一体积。二进制 JSON 保留字段名时压缩有限；当数据规模大或内部通信频繁，可评估模式驱动的二进制格式。

Thrift 与 Protocol Buffers 使用字段**标签号**而非字段名编码。名称可改，已分配的标签号不能变更或复用；新增字段须让旧读取器可跳过，也须让新读取器面对旧记录时有默认值/可选语义。类型变更需检验截断、精度和重复字段行为。书中 protobuf required/optional/repeated 示例反映当时语法，今天具体规则须查对应版本规范。

Avro 数据通常不携带字段标签，解码时同时用写入者模式和读取者模式按字段名匹配。读者缺字段时用默认值；写入者多余字段可忽略。字段新增或删除的双向兼容需要默认值；nullable 要显式 union。字段重命名可用 alias，但兼容方向不对称。写入模式可随文件存一次、随记录保存版本号/模式哈希，或在连接建立时协商。动态从关系表生成模式是 Avro 的适用场景之一。无论选择哪种格式，建立模式登记与兼容性检查比只选择“紧凑的字节格式”更关键。

## 三条数据流

**数据库**：今天的写入会被未来版本读取。滚动升级时旧代码也可能读到新代码写的记录；若旧代码读取后重写，必须确认未知字段被保留，避免静默丢失。数据库内不同记录可能来自不同年代；模式演化不能假定一次部署会重写所有历史记录。归档快照可借复制机会统一编码或转换成列式格式。

**服务 API**：服务对外暴露受业务规则限制的接口，客户端与服务端需可独立部署。REST 利用 HTTP 的资源、方法和缓存语义；SOAP/WSDL 与 RPC 有不同工具和互操作成本。远程调用有超时、丢请求/丢响应、重试导致重复执行、变动延迟和跨语言类型转换，不能当作本地函数。设计超时、重试、幂等键/去重、版本策略和可观察性。若通常先升级服务端再升级客户端，请重点验证新服务端接收旧请求，以及旧客户端解析新响应；对外 API 的客户端升级不可控，要规划长期支持。

**异步消息**：broker 缓冲、重投递、解耦生产者与消费者，也意味着消费者可能重复收到消息、处理顺序及投递语义取决于实现。消息体只是字节，应采用可演化模式；中转消费者再次发布时也要保留未知字段。分布式 actor 同样需要跨版本消息兼容，不能因统一框架而忽略网络失败。

## 第二部分导言：为何分布

第 3427—3512 行介绍分布式数据的动机：容量/负载扩展、容错和跨地域低延迟。纵向扩容与共享磁盘架构受成本或争用限制；shared-nothing 让节点独立用 CPU、内存和磁盘，以软件在网络上协调，带来运维、数据模型和一致性复杂度。**复制**是同一数据多份，主目标是冗余并可分担读；**分区**是数据拆成子集以分摊负载。两者可并用，例如每个分区有多个副本，但概念不同。先证明单机瓶颈与可用性目标，再承担分布式成本。

## 可执行检查

1. 列所有写入者和读取者，包括旧客户端、滚动升级节点、历史数据库记录和离线消费者。
2. 为每个字段变更测试四组组合：旧写旧读、旧写新读、新写旧读、新写新读；补测“旧读后重写新记录”。
3. 对重要 ID、时间、金额、二进制和可空字段建立跨语言往返测试。
4. 为服务调用验证超时、丢响应、重试与重复执行；为消息验证重复消费、版本混跑与未知字段转发。
5. 用模式登记和部署门禁记录兼容性；若需破坏兼容，制定双读/双写、迁移和旧客户端退役方案。
